Design · inpage-wallet

Inpage Wallet

One open-source, headless package that injects wallet providers into any web page, carries their requests to a host, and routes them. Any wallet app or browser extension consumes it with its own brand, its own networks, its own UI, its own storage, and its own signers. Trustodian extension and afridax mobile are the first two.

Scope

Today the extension has seven typed injectors bundled by Vite, and the mobile branch has two hand-written ES5 string templates plus a pure, tested router. Both hard-code the same wallet identity, the same channel, and the same method names, and they are already drifting in direction names, timeouts, and the window.ethereum policy.

The package takes over everything that is the same in both places and nothing that is different:

In the package shared

  • Protocol: channel, envelope, error codes, typed method map
  • Injected providers for EVM, Solana, Cardano, Tron, XRP, BTC
  • Transport shims for the extension content script and the React Native WebView
  • Router core: method classification and dispatch, with every decision behind a callback
  • Origin helper and request-id correlation
  • Parsed request models for rendering, such as EIP-712 fields

Stays in each app host

  • Connect, sign, and chain-switch UI
  • Session storage: local cache plus your backend
  • Network definitions and their ids
  • Signers and key material
  • RPC clients and node URLs
  • Tab management, WalletConnect, approval windows
  • Brand identity values, passed in as config

Requirements. Zero runtime dependencies in the injected core. Per-chain entry points so a host importing EVM never bundles Tron. Runtime config for network and identity, never build-time env. No React, no React Native, no component library inside the package. Nothing Trustodian-specific in the source: no brand name, no uuid, no RPC hosts, no keys. Everything a wallet is comes in through config.

Independence. No dependency on WalletConnect, Reown, wagmi, viem, web3.js, or any chain SDK. The package defines its own ChainType, Session, and error types rather than importing either app's. A host that also speaks WalletConnect may route both into the same modal, but the package never knows.

Layers

Four layers sit between a dApp and the user's approval. The two outer ones belong to the platform; the two inner ones are the package. Only the transport differs between the extension and mobile, and it is about fifty lines each.

Note the router runs on the host side of the transport, never in the page. The page only ever holds a thin provider that forwards calls. This is what keeps key material and session state out of reach of dApp scripts on both platforms.

Package layout

Its own repository, published to npm. Subpath exports keep every chain and every transport separately importable, with sideEffects: false so tree shaking works. Examples live beside the source so a new consumer can copy a working integration instead of reading the two production apps.

Injected side

Each chain is a factory that takes a bridge and a config and registers itself on the page. Source is TypeScript. The build turns it into an IIFE, and that IIFE is what both the Firefox content-script registration and the React Native WebView receive. Mobile stops hand-writing ES5 strings.

// injected/index.ts
export type WalletIdentity = {
  name: string;         // "Trustodian Wallet"
  rdns: string;         // "com.trustodian.wallet" — permanent, dApps key saved connections on it
  uuid: string;         // EIP-6963 uuid — permanent
  icon?: string;        // data URI; a spec-valid fallback is used until the host sends one
};

export type InjectedConfig = {
  identity: WalletIdentity;
  networks: NetworkDef[];                // your ids, your names; families decide which provider is injected
  defaultNetwork?: Record<ChainFamily, string>;   // which network answers eth_chainId before a session exists
  legacyGlobals?: {                      // off by default: EIP-6963 / Wallet Standard only
    ethereum?: boolean;                  // define window.ethereum if absent
    tronWeb?: boolean;                   // full TronWeb SDK instead of thin tronLink bridge
  };
  channel?: string;                      // defaults to "inpage-wallet-v1"
};

export function createInjectedWallet(transport: PageTransport, config: InjectedConfig): void;

Networks are yours to name

The package knows six families, one per provider standard it can speak. It does not know any network. You register networks with your own ids, the same ids your backend uses, and the package maps them to what each standard expects on the wire.

export type ChainFamily = "evm" | "solana" | "cardano" | "tron" | "xrp" | "btc";

export type NetworkDef = {
  id: string;                    // your id: "1", "11155111", "sol_mainnet", "tron_shasta", "afridax_mainnet"
  family: ChainFamily;
  name: string;                  // shown in your UI only
  wire: {                        // what the dApp-facing standard needs
    evmChainId?: string;         // hex, for eth_chainId / EIP-3326
    walletStandardChain?: string;// "solana:mainnet" for Wallet Standard
    cardanoNetworkId?: 0 | 1;
    caip2?: string;              // "eip155:1", used in parsed models and events
  };
};

// afridax mobile registers what its backend already calls things
const networks: NetworkDef[] = [
  { id: "1",            family: "evm",    name: "Ethereum",      wire: { evmChainId: "0x1", caip2: "eip155:1" } },
  { id: "11155111",     family: "evm",    name: "Sepolia",       wire: { evmChainId: "0xaa36a7" } },
  { id: "sol_mainnet",  family: "solana", name: "Solana",        wire: { walletStandardChain: "solana:mainnet" } },
  { id: "tron_shasta",  family: "tron",   name: "Tron Shasta",   wire: {} },
];

A dApp's wallet_switchEthereumChain arrives as a hex chain id; the router looks it up in this registry and stores your id in the session. An own EVM network, an L2 you operate, or a partner chain is one more entry. A dApp asking for a chain you have not registered gets 4902, or reaches ui.addChain if you provide it.

Every chain module is a thin bridge and carries no crypto. Bytes cross the boundary as plain number arrays, which the extension already does for Solana. The one exception is the full TronWeb SDK, which is a separate entry with TronWeb as a peer dependency so nobody pays for it by accident.

Transport

Two interfaces, one per side of the boundary. The page side is what the injected providers call; the host side is what the router is wired to. Each platform implements both halves in its own way.

// page side, runs inside the dApp document
export interface PageTransport {
  post(env: PageToHost): void;
  onMessage(handler: (env: HostToPage) => void): void;
}

// host side, runs in the service worker or the app process
export interface HostTransport {
  deliver(origin: string, env: HostToPage): void;
  onMessage(handler: (origin: string, env: PageToHost) => void): void;
}

Origin is never read from the page. The mobile branch's rule that origin goes null during a cross-origin navigation moves into the package's origin helper so the extension gets the same guarantee if it ever needs it.

Host side and your modal

The router is headless. It classifies a request, checks the session, and then hands every user-facing decision to a callback you supply. What you render is yours: the mobile bottom sheets, the extension's detached confirmation window, a native Swift sheet, or anything else.

Signing is the host's job entirely. ui.sign receives a parsed request and returns whatever the chain expects back. How the host produces that, from a local key, a vault iframe, an MPC service, or a hardware device, is invisible to the package. On afridax mobile today the sign callback pushes into the WalletConnect pending-request store so one modal serves both transports. That stays a mobile detail; the package has no WalletConnect import.

export type UiHandlers = {
  // Show your connect prompt. Resolve with the chosen wallet, or null if declined.
  connect(req: ConnectRequest): Promise<ConnectDecision | null>;

  // Show your sign prompt. Resolve with the signature / signed bytes / tx hash, or throw an RpcError.
  sign(req: SignRequest): Promise<unknown>;

  // Optional. Default: silent switch if the chain is supported, 4902 otherwise.
  switchChain?(req: SwitchChainRequest): Promise<boolean>;
};

export type Session = {
  origin: string;
  family: ChainFamily;
  networkId: string;             // your id from NetworkDef
  accounts: string[];
  walletId?: string;             // your wallet / vault reference, opaque to the package
  id?: string;                   // backend session id once persisted remotely
  createdAt: number;
  lastUsedAt: number;
};

export type SessionStore = {
  get(origin: string, family: ChainFamily): Promise<Session | null>;
  set(session: Session): Promise<void>;
  clear(origin: string, family: ChainFamily): Promise<void>;
  list(): Promise<Session[]>;
  // Optional: the host tells the router a session ended elsewhere (backend revoke, other device).
  subscribe?(listener: (change: { origin: string; family: ChainFamily; session: Session | null }) => void): () => void;
};

export type Policy = {
  readRpc?: "allowlist" | "none" | ReadonlySet<string>;   // default "allowlist"
  silentReconnect?: boolean;                             // default true

  supportedEvmChainIds?: ReadonlySet<string>;            // hex; default: all
};

  handle(req: { origin: string; method: string; params?: unknown[] }): Promise<RouterOutcome>;

}

Sessions: local cache plus your backend

The store is async so it can be backed by an API. dApps call eth_accounts on every page load, so the host keeps a local cache in front of the backend and writes through. The package ships a small helper for that shape; the backend client is yours.

import { layeredSessionStore } from "inpage-wallet";

const sessions = layeredSessionStore({
  local:  chromeStorageSessions,          // or MMKV on mobile: sync, answers reads
  remote: {                               // your API client, all optional
    upsert: (s) => api.post("/dapp-sessions", s).then((r) => r.id),
    remove: (id) => api.delete(`/dapp-sessions/${id}`),
    list:   () => api.get("/dapp-sessions"),
  },
  // On login or on a push notification, pull the backend list and reconcile:
  // sessions removed remotely are cleared locally and the router emits disconnect to the page.
});

What the backend gains from this: a "connected dApps" list per user across extension and mobile, revoke from any device or from the admin panel, and an audit trail of which wallet was connected to which origin. What it never receives: key material, request params, or signatures. Those pass through ui.sign only.

The request objects are typed per method, so your modal never parses raw params. For an EIP-712 request, req.typedData is already the field tree that the mobile branch renders today. The same applies to an EVM transaction summary, a Solana transaction, and a Cardano transaction once those models exist.

type SignRequest =
  | { chain: "evm";    method: "eth_signTypedData_v4"; origin; session; typedData: Eip712Tree; raw: unknown[] }
  | { chain: "evm";    method: "eth_sendTransaction";  origin; session; tx: EvmTxSummary;   raw: unknown[] }
  | { chain: "evm";    method: "personal_sign";        origin; session; message: string;   raw: unknown[] }
  | { chain: "solana"; method: "solana_signTransaction"; origin; session; txBytes: Uint8Array; raw: unknown[] }
  | …

Rule. Every decision the router can make without asking must also be overridable through Policy or a callback. Read-only answers, the RPC allow-list, silent reconnect, and auto chain-switch each have a default and a switch.

Optional default UI

Not in the core. If a third product ever wants a working browser in a day, a separate inpage-wallet-ui-rn can ship a themeable connect sheet and sign modal that implement UiHandlers. The two current apps do not need it.

Request lifecycle

One eth_sendTransaction from a dApp, end to end. The same path applies to every chain; only the classification and the model handed to the modal change.

Read-only calls such as eth_chainId and eth_accounts short-circuit at the router and never reach a callback. Allow-listed RPC reads go to deps.rpc. Connect requests for an origin that already has a session return immediately. Only genuinely new decisions reach your UI.

Protocol contract

The wire format is what both apps already speak, with the naming settled once. Unchanged values are kept byte-for-byte so a package upgrade never invalidates a saved dApp connection.

export const DEFAULT_CHANNEL = "inpage-wallet-v1";   // per-config; carried only between page and host of the same build, never persisted

export type PageToHost =
  | { kind: "ready"; chains: ChainId[] }
  | { kind: "request"; id: string; method: string; params?: unknown[] };

export type HostToPage =
  | { kind: "init"; icon: string }
  | { kind: "response"; id: string; result?: unknown; error?: RpcError }
  | { kind: "event"; chain: ChainType; event: "accountsChanged" | "chainChanged" | "disconnect"; data: unknown };

export type Envelope = { channel: string; direction: "page-to-host" | "host-to-page" } & (PageToHost | HostToPage);

// The typed method map is the part both routers hand-list today.
export interface MethodMap {

Build outputs

One source tree, three shapes of output. The package builds with tsup or Vite lib mode for the ESM parts, and a small script that runs Vite in IIFE mode once per chain for the injected bundles.

The IIFE strings are embedded into the script builder at build time, so the mobile app imports one function and no file system access is needed at runtime.

Both apps keep their current user experience unchanged. The extension keeps its detached window and its 180 second timeout. Mobile keeps its sheets, MMKV, and the WalletConnect responder. What they stop doing is maintaining two copies of the protocol. The IDENTITY object in each app is the only place the Trustodian name, rdns, and uuid exist.

Public repository

Open-sourcing injected wallet code is normal practice. MetaMask, Phantom, Rabby, and Coinbase Wallet all publish theirs, and dApp maintainers expect to read it when debugging a connection. What matters is that nothing product-specific rides along.

What the repo contains

  • License. MIT. Short, permissive, what every wallet SDK in the ecosystem uses, and no patent clause to explain to a partner's legal team.
  • CI on every pull request. Typecheck, unit tests with vitest, the jsdom announce tests for every chain IIFE, and a size-limit check against the targets above so a stray import cannot double the EVM bundle unnoticed.
  • Releases through changesets. Each PR adds a changeset; merging to main opens a version PR; merging that publishes to npm with provenance from GitHub Actions. No publishing from a laptop.
  • Examples that run. A minimal MV3 extension and a minimal Expo WebView screen, each wired with a plain confirm dialog as the modal. They double as smoke tests for the two transports.
  • A protocol document. The envelope, the method map, and the error codes as prose, versioned with the package, so a host written in Swift or Kotlin someday can implement the host side without reading TypeScript.

What must never be in it

  • Wallet identity: name, rdns, uuid, icon. These live in each consuming app and arrive as config.
  • RPC endpoints, Blockfrost or TronGrid keys, and any host URL. The read-RPC proxy calls a function the host supplies.
  • The test dApps and any signing, key, or vault code from either app. The package stops at the sign callback.

Local first, npm later

The repo is separate from day one but stays unpublished until the API settles. package.json is written as if publishing today: exports map, files, sideEffects: false, publishConfig.access: public, and a prepare script that builds dist/. That way consumers install from a path now and from npm later with no change to their imports.

yalc for mobile rather than a symlink, because Metro resolves symlinked packages unreliably across Expo versions and copying sidesteps it. When the first npm release goes out, the only change in either app is the version specifier.

Consumers beyond these two

Any wallet that renders a web page and can execute script in it can host the package: another browser extension, an Electron or Tauri desktop wallet, a Flutter or native app with a WebView. The injected side is the same IIFE string in every case. The host side needs a HostTransport for that platform, about fifty lines, and the three callbacks. A host not written in TypeScript implements the protocol document instead of importing the router.

Because the channel is only spoken between a page and a host built from the same version, a major bump never breaks a user's saved dApp connections. Those are keyed on identity, which the package does not own.

Migration

The extraction runs in two directions. Injected providers come from the extension, because they are typed and cover seven chains. The router and origin helper come from mobile, because they are pure and tested. Each step leaves both apps working.

  1. Create the repository

    A separate local git repo with license, CI, changesets, and a publish-ready package.json, but no npm release yet. Then the protocol module, both transport interfaces, typed method map, build scripts, and the jsdom announce test.

  2. Port the seven injectors

    Copy each in as a factory over PageTransport, stripping identity and network into config. The extension links the local package and its src/provider files shrink to a few lines. Firefox and Safari load the package IIFEs. Verified against test-dapps. No behavior change.

  3. Lift the router from mobile

    bridge-router.ts, origin.ts, and their tests move in with the callback names generalized and the app's EChainType replaced by the package's own. request-bridge.ts, which touches WalletConnect, stays on mobile. providerRouter.ts in the extension becomes a thin adapter and gains the read RPC allow-list for free.

  4. Add the React Native transport and script builder

    Replace the two hand-written templates on mobile with package output. Fix the empty-icon init on the way. Settle the window.ethereum policy as config.

  5. Consume from mobile via yalc

    afridax mobile takes the local package. Cardano, Tron, XRP, and BTC become one line each once mobile has host handlers for them.

  6. Add the backend session sync

    A dapp-sessions resource on the afridax backend, and the remote half of the layered store in both apps. Local-only storage keeps working until then, so this step can land independently.

  7. Publish 1.0 when the API stops moving

    Claim the npm scope, publish from CI, and switch both apps from path installs to a version. Protocol changes after 1.0 bump the major and the default channel suffix together.

Sequencing. AFX-1119 is unmerged and still receiving fixes. Start the package after that branch lands so step 3 lifts a stable router instead of chasing one.

Open decisions

  • window.ethereum. Keep the extension strict and mobile permissive through config, or align both. Recommendation: off by default, on for mobile only, because in-app browsers meet older dApps that never adopted EIP-6963.
  • Backend session schema. Which fields the backend stores per session and who can revoke. Proposal: origin, family, networkId, accounts, walletId, device, createdAt, lastUsedAt; revoke by user from any device and by admin.
  • Tron. Ship the thin tronLink bridge as the default and keep the full TronWeb entry for the extension only. Mobile decides when it adds Tron.
  • Solana signing on mobile. The provider announces sign features that the host rejects today. Either finish the host side before the package lands on mobile, or let the config drop the unsupported features from the announcement.
  • Reserve the name. inpage-wallet is free on npm today. Unscoped names get squatted; publish a 0.0.1 placeholder early even though real releases wait for the API to settle.
  • GitHub org. The repo can sit under the afridax org or a neutral one; the package name does not depend on it and a transfer later keeps the npm name.
  • What triggers 1.0. Recommendation: both apps running on the package in production for one release cycle with no protocol change. Until then the version stays 0.x and breaking changes are allowed.
